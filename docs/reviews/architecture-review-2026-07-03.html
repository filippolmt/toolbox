1 · The Bridge Contract is a comment, not a seam

internal/bridge/paths.go · internal/build/assets/bin/bridge-lib.sh

Strong

Problem

The container→host request path is one contract split across two languages with no binding test. paths.go defines the socket path (ContainerSocket = ".../run/bridge.sock") with the comment "Must match BRIDGE_SOCK in bridge-lib.sh"; bridge-lib.sh re-hardcodes the same literal. The legacy fallback path is duplicated the same way. The invariant lives only in a comment — a rename on either side silently breaks the socket-first transport, and nothing fails until a user's xdg-open stops reaching the host.

Deletion test

Fails — this is genuine cross-language coupling that no module boundary contains. That is exactly the signal for a deepening.

Solution (plain English)

Give the daemon↔shim wire contract a name and one owner. The Go side becomes the single source of the path/port/token/header literals; the shell shim reads them (env-injected at container create, or a generated fragment) instead of re-typing them. A single test asserts the Go constants and the shell shim agree — the same move that turned the init.d bijection and Tool Catalog fan-outs into red-on-drift tests.

Benefits

  • Leverage: one edit site for the wire format, not two-in-two-languages.
  • Locality: "how a request travels" reads from one named module.
  • Tests: drift becomes a failing Go/smoke test, not a field-reported broken bridge.

2 · config show renderer trapped in cmd

cmd/config.go:353–572 (~220 lines)

Strong

Problem

A hand-rolled YAML serializer (writeResolvedConfigWithOrigin, writeSortedMap, writeYAMLSlice, quoteIfEmpty, boolPtrStr) lives in the cobra layer, mirrors the Config Schema field-by-field, and is keyed off the package var cfg. It is real logic coupled to config internals but sitting a package away from them — testable today only by holding the whole schema-coverage test (TestConfigShowCoversSchema) in cmd.

Deletion test

Concentrates — a config.Render(w, cfg, prov) module would sit beside the schema it already duplicates, and the coverage test would guard the renderer from inside the package it reflects.

Solution (plain English)

Move the serializer into internal/config (or a sibling it owns) as one exported rendering seam that takes a writer + resolved config + provenance. cmd shrinks to "load, call Render, print". This is the exact deepening already applied to Config Schema, Config Plan, and the annotated example — a fifth schema consumer joining the reflected-tag authority instead of hand-enumerating beside it.

Benefits

  • Locality: renderer lives next to the schema it must track.
  • Tests: render becomes a pure table test (input config → golden YAML), no cmd, no cobra, no package var.
  • Leverage: one more red-on-drift schema consumer; AI-navigable "where is config printed" → one owner.

3 · internal/ui — a seam nobody crosses

internal/ui/output.go (34 lines) · ~50 raw "toolbox:" call sites in cmd

Worth exploring

Problem

Two competing output conventions coexist. internal/ui wraps fmt.Fprintln(os.Stderr, …) with an OK:/WARN: style — but it is called from cmd once (build.go:38). The convention users actually see is copy-pasted raw: ~24 "toolbox: warning: …" strings and ~26 fmt.Fprintln(os.Stderr, "toolbox: …") across shell.go, worktree.go, root.go and more. The seam that should own CLI output is dead weight while the real style has no owner.

Deletion test

Deleting ui today concentrates nothing (one caller) — proof it is shallow. The deepening is the inverse: make it the actual owner of the toolbox: convention so it earns its keep.

Solution (plain English)

Pick one convention (the toolbox: warning: prefix users already see), express it once in ui, and route every cmd call site through it. The prefix, the stderr target, and the styling become one decision behind one seam instead of ~50 string literals.

Benefits

  • Leverage: change the prefix / add color / add a --quiet in one place.
  • Tests: output format asserted once, not per-handler.
  • Consistency: kills the two-styles drift; every message reads the same.

4 · The config "key" has no home (TUI)

internal/configui/model.go · adapter.go · rows.go · view.go

Worth exploring

Problem

Adding one config key means editing ~10 parallel switch key {…} blocks smeared across four files: openEditor, saveMulti, displayValue, collectionNoun, detailEntries, StringValue/BoolValue/ListValue/EnumOptions, saveRows, previewDoc, nodeDisplay. The per-key knowledge is a Repeated Switch over the same type — the classic shallow smell. (The tea Model/Update/View seam itself is clean and terminal-free; this is only the key metadata.)

Deletion test

The switches merely move complexity — each new key re-fans across ten sites. A key descriptor table would concentrate it.

Solution (plain English)

One typed descriptor per config key (label, kind, editor, enum options, display, noun) in a single table the ten sites read — the same shape Tool Catalog used to collapse three parallel literals into one declaration. Adding a key becomes one row. Best if it can derive from, or be coverage-tested against, Config Schema so the TUI can't silently omit a field.

Benefits

  • Locality: everything about a key in one row.
  • Leverage: ten switches become ten table lookups.
  • Tests: a schema-coverage test catches an un-described key (kills the dead OriginExplicit branches too).

5 · A second, un-seamed Docker edge in cmd

cmd/shell.go:164 (resolveImageDigest) · cmd/worktree.go:220,511,528

Worth exploring

Problem

Almost every Docker op goes through the container module, but resolveImageDigest reaches past it — cli.ImageInspect(ctx, ref) then unpacks RepoDigests via the pure build.RepoDigest — and client.APIClient is threaded raw through three worktree sites. So the Docker edge is split: container owns most, but a lone ImageInspect caller lives in cmd, imported straight from moby/client.

Deletion test

The orchestration is genuine, but the SDK call is in the wrong module. Folding ImageInspect behind container concentrates the daemon edge; leaving it keeps a second un-seamed caller that tests must mock separately.

Solution (plain English)

Add the digest lookup to the container seam (e.g. a ResolveDigest(ref) the module owns), so cmd stops importing moby/client for anything but the shared shell launch. This mirrors how Docker Identity and Session Plan keep all daemon-edge state on one side of a single seam.

Benefits

  • Locality: one place answers "who talks to the daemon".
  • Tests: cmd no longer needs its own Docker mock for digest resolution.
  • Leverage: future image ops attach to the same seam.

6 · TUI preview rebuilds what the writers write

internal/configui/view.go:230–289 vs adapter.go:453–532

Speculative

Problem

previewDoc/rowsPreviewDoc rebuild "what will be written" as a map[string]any, entirely independent of the real yaml.Node writers SaveMap/SaveShells/SaveSeed. Two representations of the same pending mutation — the preview can silently diverge from what actually lands in the file.

Deletion test

The preview duplicates the write model rather than deepening it. Why Speculative: the drift risk is real but low-blast (a wrong preview, not a wrong write) and a rework touches the render path.

Solution (plain English)

Derive the preview from the same pending-mutation model the writers consume — render the diff the writers will apply, rather than re-deriving it. One description of "the pending change", two views (preview + write) over it.

Benefits

  • Locality: pending change described once.
  • Correctness: preview cannot lie about the write.

★ Top recommendation

Tackle Candidate 1 — the Bridge Contract first. It is the only finding whose deletion test fails outright: the coupling is real, cross-language, and contained by no module — it lives in a comment. Every other candidate is a quality/locality improvement over code that already works; this one guards against a silent production break (a path rename that stops xdg-open reaching the host with no failing test). And the fix is idiomatic here — it is the same bijection-test move the repo already trusts for the init.d and Tool Catalog fan-outs.

Safest first win, if you'd rather bank an easy one: Candidate 2 — config.Render. It is a pure lift-and-shift into a package that already owns the schema, unlocks a golden test, and mechanically extends the established Config Schema deepening. Lowest risk, clear leverage.
